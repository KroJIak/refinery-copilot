# 13 — Сценарии (`scenarios.py`)

Пресеты входов для headless-прогонов и демо: каждый сценарий — конкретизация канонической формы
[[06-scenario|Scenario]] ([[06-scenario]]): `kind`, `t_point`, `overrides`, `seed`, `description`. Пресеты
служат трем целям сразу: CLI-демо ([[14-cli]]), фикстуры фронта (api/90-examples-and-mocks.md)
и тесты ([[15-tests]]). Требование к демонстрации: «полный цикл взаимодействия агентов —
от входных данных до финальной рекомендации» на устойчивом периоде, периоде риска и ситуации
с плохими данными.

## Scope

| | |
| --- | --- |
| **Содержит (covers)** | 4 демонстрационных сценария (норма / риск 2026 / плохие данные / сернистая нефть) с параметризацией `t_point`, `overrides` и ожидаемым исходом; правило «нежёсткости» — сценарий реагирует на изменение задания по качеству; валидация `overrides` (только управляемые); связь пресетов с фикстурами и CLI |
| **НЕ содержит (does NOT cover)** | CLI-парсинг аргументов ([[14-cli]]); логику агентов ([[09-agent-orchestrator]]); генерацию мок-SSE на фронте (frontend/05-mocks.md); подмену данных в Parquet-хранилище (инжест — data-pipeline) |

## Перечень сценариев

Четыре демонстрационных сценария `make demo` (см. [[14-cli]]):

| # | `kind` | Описание | `t_point` | `overrides` / подмены | Ожидаемый исход |
| --- | --- | --- | --- | --- | --- |
| 1 | `normal` | Устойчивый период: «система не создаёт лишних управляющих действий» | спокойный день 2024 года, свежий ЛИМС | нет | `recommend` с сохранением режима (малые дельты) и запасом по всем целям |
| 2 | `quality_risk` | Сырьё/режим у границы спецификации: средняя сера близка к норме 10 мг/кг (параметр сценария) | июнь 2026, свежий ЛИМС | нет (состояние 2026 само по себе рискованное) | `recommend` со снижением серы (рост T ГСС / режим блендинга), `spec_risk` заметно > 0 |
| 3 | `bad_data` | Плохие данные: сентинелы в ключевых каналах + старый ЛИМС | любой; подмены входа | сентинел-подмены ключевых каналов; возраст ЛИМС > 52 ч | **гарантированный отказ** `refuse` (`stale_lims` + `sensor_fault`; при живых каналах — `wide_interval`) |
| 4 | `sour_crude` | Сернистая нефть: выросла сера на входе АВТ → сера прямогонного ДТ | рядом с `quality_risk` | переопределение входного качества сырья через `overrides` управляемых + состояние сырья | `recommend`: изменение температуры входа в реактор и режима блендинга, чтобы выдержать спецификацию |

> [!note] Пятый `ScenarioKind`
> Enum B.5 [[01-enums]] содержит и `stale_lims` — «чистый» пресет отказа по свежести без сентинел-подмен.
> В `make demo` он не входит (4 сценария демо, отказ уже показан в `bad_data`), но используется
> в тестах [[15-tests]] и доступен через CLI `--scenario stale_lims`.

## Параметризация входов

```python
PRESETS: dict[ScenarioKind, ScenarioPreset] = {
    ScenarioKind.normal: ScenarioPreset(
        t_point=datetime(2024, 5, 15, 8, 0, tzinfo=UTC),   # спокойный период
        overrides={},                                       # штатный режим без вмешательств
        seed=42,
        description="Устойчивый режим: лишних действий нет",
    ),
    ScenarioKind.quality_risk: ScenarioPreset(
        t_point=datetime(2026, 6, 15, 8, 0, tzinfo=UTC),    # хвост периода — holdout 2026
        overrides={},
        seed=42,
        description="Средняя сера у границы нормы 10 мг/кг (значение настраивается)",
    ),
    ScenarioKind.bad_data: ScenarioPreset(
        t_point=datetime(2026, 6, 15, 8, 0, tzinfo=UTC),
        overrides={},
        fault_injection=FaultInjection(                     # подмены ДО конвейера:
            sentinel_tags=["24-2000.Q21", "24-2000.W4"],    #   сентинелы 307/251/252/240
            lims_age_hours=60.0,                            #   ЛИМС старше stale_after_h = 52 ч
        ),
        seed=42,
        description="Сентинелы в ключевых каналах + устаревший ЛИМС → отказ",
    ),
    ScenarioKind.sour_crude: ScenarioPreset(
        t_point=datetime(2026, 6, 15, 8, 0, tzinfo=UTC),
        overrides={"blend_share_kerosene": 0.12},           # пример: доля керосина в бленде
        seed=42,
        description="Сернистая нефть: сдвиг качества сырья на входе цепочки",
    ),
}

def resolve_scenario(kind: ScenarioKind, overrides: dict[str, float] | None = None,
                     t_point: datetime | None = None, seed: int = 42) -> Scenario:
    """Пресет + пользовательские переопределения. Валидация:
    1. Ключи overrides — ТОЛЬКО управляемые ([[07-agent-optimization]]): P8/T11/F19,
       АВТ-переменные, доли бленда, присадка. Неуправляемый ключ → ошибка 400 (P1).
    2. t_point — внутри обученных данных (границы из [[08-model-artifact]] trained_on_range).
    3. seed >= 0 фиксируется до первого шага прогона."""
```

Подмены `FaultInjection` применяются **до** конвейера агентов и честно отражаются в трейсе:
агент данных видит ровно то, что видел бы оператор (сентинелы в сырых значениях, старую метку
ЛИМС) — подмена не «вклеивает» нужный отказ искусственно.

## Свойство «реагируют на изменение входов»

> [!important] Сценарии не «жёсткие»
> «Сценарии не "жёсткие": результат должен меняться при изменении входов — и качества сырья,
> и задания на качество продукции». Пример: «изменилась сера в нефти на АВТ →
> изменилась сера прямогонного ДТ → система рекомендует изменение температуры входа в реактор
> гидроочистки и режим блендинга, чтобы выдержать спецификацию».

Следствия для реализации:

1. **Задание по качеству — параметр сценария.** Целевая спецификация (лето/зима: ЦЧ ≥ 51/49,
   плотность 820–845 / 800–845) подаётся как настройка прогона, а не константа ядра; смена
   задания меняет пороги [[06-constraints-engine]] и, значит, Парето-фронт ([[08-pareto-front]]).
2. **Проверка реакции** — часть acceptance-критериев: один и тот же `t_point`, но разное задание
   (лето ↔ зима) обязано дать разные `actions`/`checks`; тест — в [[15-tests]].
3. **Чувствительность** как санити: «~0,3 мг/кг серы на 1 °C температуры реактора»
   — ответ на сдвиг сырья должен быть того же порядка.
4. Никаких «зашитых» ответов: пресеты задают только входы; исход каждого сценария проверяется
   тестами как класс исхода (recommend/refuse), не как фиксированный JSON (числа могут уточняться
   при обновлении моделей — фиксируются только в фикстурах api/90 для моков).

## Маппинг на фикстуры и приёмку

| Сценарий | Фикстура api/90-examples-and-mocks.md | Приёмочный признак |
| --- | --- | --- |
| `normal` | `fixtures/normal.json` | рекомендация с малыми дельтами; все `checks` passed; лишних действий нет |
| `quality_risk` | `fixtures/quality_risk.json` | `spec_risk` заметно > 0; действия снижают серу; Парето-фронт показан |
| `bad_data` | `fixtures/refusal.json` | `refusal.reasons` непуст; текст отказа по шаблону; трейс агентов полный |
| `sour_crude` | `fixtures/sour_crude.json` | `actions` отличаются от `normal` при том же задании — реакция на сдвиг сырья |

Каноническая форма пресета (пример A.6 [[06-scenario]]):

```json
{"scenario_id": "b41d9f02", "kind": "quality_risk", "t_point": "2026-06-15T08:00:00Z",
 "overrides": {"blend_share_kerosene": 0.12}, "description": "2026 прижат к границе по сере", "seed": 42}
```

## Порядок обновления пресетов

1. Меняется состав управляемых переменных ([[07-agent-optimization]]) → правятся допустимые
   ключи `overrides` и валидатор `resolve_scenario` — одна правка, одно место истины.
2. Обновляются модели/данные → все `t_point` пресетов перепроверяются на попадание в новый
   `trained_on_range` артефактов [[08-model-artifact]].
3. Числа фикстур api/90 обновляются **только** фактическим прогоном CLI ([[14-cli]]); ручное
   редактирование чисел в фикстурах запрещено — расхождение фикстур с ядром = баг контракта.

## Связи

- **[[06-scenario]]** (api): каноническая форма и ограничения на `overrides` — здесь пресеты,
  там контракт.
- **[[14-cli]]**: `make demo` / `python -m refinery_core.demo` прогоняют пресеты headless.
- **api/90-examples-and-mocks.md**: статические фикстуры 4 сценариев + отказ для автономного фронта.
- **[[15-tests]]**: каждый пресет имеет тест-класс исхода; `stale_lims` — отдельный тест отказа.

## Правила дизайна

> [!warning] Ключевые правила
> 1. Пресет = только входы (t_point, overrides, подмены, seed); никакой логики исходов.
> 2. `overrides` — только управляемые переменные; валидация до старта прогона.
> 3. Подмены плохих данных — до конвейера, видны агентам как реальные сырые данные.
> 4. Сценарий обязан реагировать на смену задания по качеству — иначе он «жёсткий» и неверен.
> 5. Один seed на сценарий; смена seed'а меняет только run_id/тайминги, не числа решения.
