# 06 — Движок жёстких ограничений (`optimize/constraints.py`)

## Scope

Общий сервис ядра: проверяет вариант крутки (и текущее состояние) против жёстких ограничений —
спецификации продукта, материального баланса блендинга и модельных диапазонов переменных —
и выдаёт машиночитаемый список проверок с вердиктом «нарушено / на грани / ок».

**Покрывает:** реестр ограничений (сера ≤ 10 мг/кг, T95 ≤ 360 °C, ЦЧ ≥ 51/49, плотность
820–845 / 800–845, доли = 100 %, присадка ≤ 3 %, диапазоны p2/p98); правила выбора проверяемого
значения; машину вердиктов с гистерезисом; формат выхода `checks[]`.
**Не покрывает:** экономику и ранжирование ([[08-pareto-front]]); генерацию вариантов
([[07-agent-optimization]]; движок только фильтрует); решение об отказе ([[10-refusal]]);
поля DTO — `CheckItem` из [[04-recommendation]], флаг значения — [[01-enums|QualityFlag]].

> [!quote] Правило приоритета безопасности
> «Качество и жёсткие технологические ограничения имеют приоритет над экономическим эффектом.
> Недопустимый режим нельзя «компенсировать» более высокой производительностью или меньшими
> затратами.»

## Реестр ограничений

| `t95_max` | T95 товарного ДТ | ≤ 360 °C | спецификация |

| `cetane_min_winter` | ЦЧ зимнего ДТ | ≥ 49 пункт | спецификация |
| `density_hdu` | плотность ДТ с гидроочистки | 820–845 кг/м³ | спецификация |
| `density_blend_summer` / `density_blend_winter` | плотность товарного ДТ | 820–845 / 800–845 кг/м³ | спецификация |

### Материальный баланс и блендинг

| id проверки | Правило | Лимит | Тип источника |
| --- | --- | --- | --- |
| `blend_share_sum` | доли компонентов (очищенный дизель, керосин, газойль) | = 100 % (допуск ±0.01 п.п.) | баланс: доли компонентов при блендинге должны составлять 100% |
| `additive_max` | дозировка цетаноповышающей присадки | ≤ 3 % | спецификация |

Зимнее/летнее исполнение выбирается по месяцу `t_point` (переходные месяцы — в конфиге);
само правило сезонности — явное допущение, фиксируемое в [[07-run-report]].

### Модельные диапазоны переменных (допущение)

| id | Переменная | Диапазон p2–p98 | Источник |
| --- | --- | --- | --- |
| `range_p8` | P8 | 0.008–0.229 | по истории данных (без сентинелов) |
| `range_t11` | T11 | 11.0–381.6 | то же |
| `range_f19` | F19 | −0.08–251.1 | то же |
| `range_t5` | T5 | 10.5–386.9 | то же |
| `range_f65` | F65, т/ч | 42.9–1181.3 | то же |
| `range_t55` | T55, °C | 20.4–385.7 | то же |
| `range_p22` | P22, МПа | 0.358–1.205 | то же |
| `range_w70` | W70, т/ч | 0.48–123.0 | то же |

> [!warning] Правило границ (дословно)
> «Если для параметра в пакете нет подтверждённого рабочего диапазона, не выдавайте
> исторический min/max за промышленный предел. Можно задать консервативный модельный диапазон
> на основе истории или литературы, но он должен быть явно помечен как допущение
> для эксперимента.»

Поэтому все проверки `range_*` несут пометку «допущение»: в `description` `CheckItem` и в
карточке они отображаются иначе, чем спецификация («рекомендация не должна выходить за явно
заданные технологические/модельные ограничения»).

## Какое значение проверяется

| Класс проверки | Значение `value` в `CheckItem` |
| --- | --- |
| Качество после крутки (сера, T95, ЦЧ, плотность) | **консервативный хвост прогноза**: p90 для верхних лимитов, p10 для нижних ([[03-quality-assessment]] после батч-прогноза варианта) |
| Баланс и присадка (доли, ≤ 3 %) | само значение варианта |
| Диапазоны переменных `range_*` | значение крутки варианта (или текущее состояние — для state-проверок) |

Консервативный хвост — прямое следствие приоритета безопасности: вариант допускается, только
если даже пессимистичный квантиль в норме. Субъективная «середина» не используется.

## Машина вердиктов: нарушено / на грани / ок

Три вердикта на проверку: `VIOLATED` (вариант отбраковывается безусловно), `BORDERLINE`
(допустим, но подсвечивается оператору и штрафуется в Парето-сравнении), `OK`. Граница
«на грани» работает с **гистерезисом**: вход в зону при малом запасе, выход — только при
заметно большем, чтобы вердикт не мигал от шума датчика (правило стабильности рекомендаций:
гистерезис, не «дёргать» оператора).

```python
class Verdict(Enum): OK; BORDERLINE; VIOLATED

BORDER_ENTER = 0.03     # вход в «на грани»: запас ≤ 3 % ширины лимита
BORDER_EXIT  = 0.06     # выход: запас ≥ 6 % — гистерезис (константы конфига, в RunReport)

def verdict(prev: Verdict, margin: float, span: float) -> Verdict:
    # margin  — запас до лимита (для двустороннего лимита: min(x − lo, hi − x))
    # span    — ширина лимита (hi − lo либо сам лимит для односторонних)
    if margin <= 0:
        return Verdict.VIOLATED                       # гистерезис не смягчает нарушение
    if prev is Verdict.BORDERLINE:
        return Verdict.OK if margin >= BORDER_EXIT * span else Verdict.BORDERLINE
    return Verdict.BORDERLINE if margin <= BORDER_ENTER * span else Verdict.OK
```

Правила машины:

1. `margin ≤ 0` ⇒ `VIOLATED` всегда: гистерезис управляет только классификацией «на грани»,
   никогда — пропуском нарушений.
2. `BORDERLINE` не отбраковывает вариант, но (а) подсвечивается в карточке, (б) даёт штраф
   в стоимостной функции Парето ([[08-pareto-front]]) — «жёлтый» вариант проигрывает «зелёному».
3. Все пороги — константы конфига ядра: детерминизм (при одинаковом состоянии системы
   численные результаты воспроизводятся).

## Качество входных значений

Проверка честна не более, чем её вход. Значение с `quality_flag != ok` ([[01-enums|QualityFlag]] —
`sentinel/stuck/outlier/missing`) **не может дать пройденную проверку**: непроверяемое
трактуется как нарушение (safety-first), а в `description` `CheckItem` попадает причина.
Это исключает ситуацию «ограничение выполнено» на мёртвом канале.

```python
    #     checks    = list[CheckItem],   # {constraint_id, description, limit, unit, value, passed} — [[04-recommendation]]
    #     feasible  = all(c.passed for c in checks),
    #     violations = [c.constraint_id for c in checks if not c.passed],

```

- `passed = (verdict is OK or BORDERLINE)` для варианта; для карточки в `checks[]` идут все
  проверки с фактическим вердиктом в описании — блок карточки «Проверка ограничений».
- `feasible=false` по всем сгенерированным вариантам — вход отказа `no_feasible_variant`:
  «все варианты отбракованы жёсткими ограничениями».
- Пример канона: `{"constraint_id": "sulfur_max", "description": "сера ≤ 10 мг/кг", "limit": 10.0,
  "unit": "мг/кг", "value": 9.8, "passed": true}` ([[04-recommendation]]).

## Приёмочные проверки (для [[15-tests]])

1. Сера p90 = 10.4 ⇒ `sulfur_max` → `VIOLATED`, вариант невидим для Парето; p90 = 9.9 при
   prev=BORDERLINE ⇒ остаётся «на грани» (не «ок») — гистерезис соблюдён.
2. Доли {0.6, 0.3, 0.09} + присадка 0.01 ⇒ `blend_share_sum` пройдена; {0.6, 0.3, 0.2} — нет.
3. Значение с `quality_flag="stuck"` ⇒ проверка не проходит; причина в описании.
4. Одинаковый вход ⇒ идентичный список `checks[]` (детерминизм, без скрытых случайностей).

[^1]: Стоимостной прокси: дозировка присадки до 3 %, но 1 т присадки в 100 раз дороже 1 т ДТ (штраф «×100» — в [[08-pareto-front]]).
[^2]: Состав правил движка: сера ≤ 10 мг/кг, T95 ≤ 360 °C, ЦЧ ≥ 51/49, плотность 820–845, доли бленда = 100 %, присадка ≤ 3 %, модельные диапазоны p2/p98 (пометка «допущение»); вердикт pass/violate + причина.
[^3]: Карточка включает блок «Проверка ограничений»: какие жёсткие ограничения проверены и выполнены.
