# 08 — Парето-фронт (`optimize/pareto.py`)

Модуль принимает `CandidateSet` от [[07-agent-optimization]] (уже отфильтрованный [[06-constraints-engine]])
и строит недоминируемое множество вариантов в осях «запас качества ↔ стоимость». Функции модуля:
вычисление осей, ранжирование по Парето, выбор точки по политике безопасности, отбор
`alternatives` для карточки [[04-recommendation]]. Жёсткие ограничения здесь не проверяются —
к этому моменту все варианты уже допустимы.

## Scope

| | |
| --- | --- |
| **Содержит (covers)** | ось качества (запас до спецификации по сере и остальным целям); ось стоимости (`cost_index` = энергопрокси + присадка ×100[^x100]); вычисление недоминируемых вариантов и `pareto_rank`; правило выбора точки по политике безопасности; отбор 3–4 `alternatives` для карточки рекомендации; сериализация визуализируемых точек в трейс шага и фикстуры [[06-scenario|Scenario]] |
| **НЕ содержит (does NOT cover)** | генерацию и оценку вариантов ([[07-agent-optimization]]); проверку жёстких ограничений ([[06-constraints-engine]]); рендер UI (frontend/08-components-recommendation-card.md); взвешенную скалярную оптимизацию с подбором весов вручную |

## Оси фронта

### Ось качества: запас до спецификации

Каждой цели `QualityTarget` соответствует спецификация ([[06-constraints-engine]]).
Запас считаем по нижней границе доверительного интервала — «планируем под P90», а не под медиану:

```python
def quality_margin(q: TargetQuantiles, limit: SpecLimit) -> float:
    """sulfur: limit 10 мг/кг  → margin = limit - p90   (чем больше, тем безопаснее)
    t95:      limit 360 °C    → margin = limit - p90
    cetane:   limit 51/49     → margin = p10 - limit
    d15:      окно 820–845 / 800–845 → min(p90 - lo, hi - p90) → нормируем в [0..1]"""
```

Сводная ось качества варианта — **минимальный нормированный запас по всем целям** (maximin-метрика):
фронт строится по худшему запасу варианта, а не по среднему. Такой выбор не даёт «протащить»
вариант с отличной серой, но ЦЧ на грани.

### Ось стоимости: энергопрокси + присадка ×100

```python
def cost_index(v: EvaluatedVariant, cfg: CostConfig) -> float:
    """cost = cfg.energy_per_sulfur_unit * max(0, baseline_sulfur_p50 - v.sulfur_p50)  # энергопрокси
             + 100.0 * v.additive_tonnes                                              # присадка ×100 к ДТ
    """
```

Два явных допущения (помечены в конфиге и в отчёте [[12-run-report]]):

1. Энергопрокси: «чем больше серы в гидроочищенном ДТ, тем дешевле его производство
   (меньше энергозатрат)». Аппроксимация линейна по снятой нагрузке
   обессеривания; коэффициент — константа конфига, не рубли.
2. «1 т присадки в 100 раз дороже 1 т ДТ — готовый стоимостной прокси для оптимизации»[^x100].`cost_index` безразмерен и используется только для **порядка** вариантов на фронте.

## Двумерный фронт «запас по сере ↔ стоимость»

Для визуализации и карточки главный срез фронта — сера (главный риск 2026 года) против стоимости:

```mermaid

    x-axis "cost_index (усл. ед.)" [0, 1, 2, 3, 4]

    line [1.8, 1.6, 1.3, 0.9, 0.4]
```

Каждая точка — вариант крутки из [[07-agent-optimization]]: больше запаса по сере = глубже
обессеривание = дороже (энергопрокси) либо дешевле без присадки, но с ростом присадки ×100 для ЦЧ.

```python
def pareto_rank(points: list[ParetoPoint]) -> list[ParetoPoint]:
    """Недоминируемость по (quality_margin ↑, cost_index ↓). Ранг 1 — фронт,
    ранг 2 — фронт без ранга 1, и т.д. Детерминированно: сортировка устойчивая,
    тай-брейки по (cost, variant_id)."""

def select_by_policy(points: list[ParetoPoint], policy: SafetyPolicy) -> ParetoPoint:
    """Политика безопасности (по умолчанию): точка с максимальным минимальным запасом
    среди точек ранга 1 с cost_index <= cost_cap (кап — конфиг, допущение).
    НЕ «самый дешёвый на фронте» и не «максимум прибыли»: безопасность важнее экономики."""
```

> [!important] Политика безопасности
> «Качество и жёсткие технологические ограничения имеют приоритет над экономическим эффектом».
> Выбор точки по умолчанию — `maximin` по запасу качества, а не минимум стоимости.
> «Экономичный» вариант с минимальным запасом попадает в `alternatives`, но не в основную
> рекомендацию. Конфликт целей разрешается в пользу ограничений (правило дизайна 4 [[core-architecture/00-OVERVIEW]]).

## Отбор `alternatives` для карточки

Карточка [[04-recommendation]] показывает 3–4 альтернативы формы `AlternativeItem`
(`{label, actions, quality, cost_index, pareto_rank}`):

| Слот | Правило отбора | Подпись в карточке |
| --- | --- | --- |
| основной | `select_by_policy` (maximin) | «Рекомендуемый вариант» |
| альт. 1 | минимальный `cost_index` на ранге 1 | «Экономичный вариант» |
| альт. 2 | максимальный запас по сере на ранге 1 | «Максимальный запас» |
| альт. 3 | лучшая точка ранга 2 (если отличается по действиям) | «Компромисс» |

Дубликаты по набору действий (`actions`) схлопываются; альтернативы с `pareto_rank` попадают
в SSE-событие `recommendation` и в отчёт [[12-run-report]].

## Визуализируемые точки и связь со сценариями

1. Точки фронта сериализуются в `output` шага optimization ([[05-agent-step]], `number_refs` на
   координаты точек) — фронтенд рисует фронт на странице what-if (frontend/13-page-whatif.md).
2. Фикстуры демонстрационных сценариев ([[06-scenario|Scenario]], api/90-examples-and-mocks.md) содержат
   готовые фронты, чтобы интерфейс работал без backend; форма точки — та же `AlternativeItem`.
3. Для сценария «риск 2026» ([[13-scenarios]]) фронт обязан показать, что рост запаса по сере
   достигается ростом `cost_index` — это и есть объяснимый компромисс, выносимый в карточку.

## Пограничные случаи

| Случай | Поведение модуля |
| --- | --- |
| Один допустимый вариант | Фронт вырожден: `pareto_rank = 1`, единственная точка — рекомендация; `alternatives` пусты |
| Тай-брейк (равные margin и cost) | Устойчивая сортировка по `variant_id` — выбор детерминирован, без случайностей |
| `CandidateSet` пуст | До фронта не доходит: пустой набор отсекается в [[09-agent-orchestrator]] → `no_feasible_variant` ([[10-refusal]]) |
| Все точки на границе `cost_cap` | Политика выбирает maximin среди доступных; срабатывание капа помечается в `notes` шага |
| Отрицательный запас (P90 за спецификацией) | Вариант не мог пройти [[06-constraints-engine]]; обнаружение здесь — баг конвейера, исключение сборки |

## Пример точки фронта (`AlternativeItem`, форма A.4 [[04-recommendation]])

```json
{"label": "Экономичный вариант",
 "actions": [{"tag": "24-2000.P8", "unit": "°C", "current_value": 341.2, "recommended_value": 342.5, "delta_pct": 0.4}],
 "quality": [{"target": "sulfur", "p10": 9.2, "p50": 9.8, "p90": 10.0}],
 "cost_index": 1.2, "pareto_rank": 1}
```

Иллюстрация сокращена до одного слота действий; полные канонические примеры карточки и
`alternatives` — [[90-examples-and-mocks]] (значения точек фронта — из фикстур api, не отсюда).
Минимальный запас экономичного варианта (P90 серы у самой границы) — ровно то, почему он
остаётся альтернативой, а не основной рекомендацией при политике безопасности.

## Правила дизайна

> [!warning] Ключевые правила
> 1. На вход — только варианты, уже прошедшие жёсткие ограничения; Парето никогда не
>    «прощает» нарушение ради стоимости.
> 2. Ось качества — по P90/P10 (худшая граница интервала), не по медиане.
> 3. Стоимость — прокси с явными допущениями; подпись «усл. ед.», не рубли.
> 4. Выбор точки — по политике безопасности (maximin), экономичный вариант — только в альтернативы.
> 5. Все координаты точек — в `number_refs` шага: числа в карточке — только из расчёта.

[^x100]: Стоимостной прокси: дозировка до 3 %, но 1 т присадки в 100 раз дороже 1 т ДТ.
