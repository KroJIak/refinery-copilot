# 01 — Соглашения имён, версий и времени

## Scope

| Раздел | Содержимое |
| --- | --- |
| **Содержит** | формулы имён файлов и каталогов; партиционирование по году; кодек и физические типы (время `timestamp[ms, UTC]`, енумы `dictionary`); правило только-добавления и версии каталогов v1/v2; sha256-хэши данных → `datasets_manifest.json` → `data_hashes` отчёта |
| **НЕ содержит** | схемы колонок конкретных датасетов ([[02-dataset-telemetry-242000]]–[[05-dataset-pak]]); содержимое `artifacts/` ([[06-artifacts-catalog]]); правила чистки (data-pipeline) |
| **Зависит на** | глобальная таблица форм ([[00-SUMMARY]]), [[03-p3-core-datastore]]/[[04-p4-pipeline-datastore]] |

## 1. Имена файлов и каталогов

Единственная форма имени файла датасета:

```text
{dataset}__{tag|point|indicator}__{yyyy}.parquet      # телеметрия, партиции по году
{dataset}__{yyyy}.parquet                             # лабораторные/анализаторы, партиции по году
```

Фактическая раскладка `data/processed/`:

```text
data/processed/
  242000__{tag}__{yyyy}.parquet      # 26 тегов × 2023–2026, напр. 242000__Q21__2024.parquet
  avt__{tag}__{yyyy}.parquet         # 71 тег (D10 исключён, см. [[03-dataset-telemetry-avt]])
  lims__{yyyy}.parquet               # все 6 точек отбора и 54 серии в одной партиции года
  pak__{yyyy}.parquet                # обе серии: 24-2000:Mg.Sulfur и 24-2000:D15
  freshness.parquet                  # снимок свежести точек контроля (канон [[02-data-freshness]]), один файл
  quality_datasets/{target}.parquet  # признаки + метки для обучения (пишет P4)
  datasets_manifest.json             # хэши, диапазоны дат, версия пайплайна
```

> [!note] Логические имена в протоколах
> В протоколах [[03-p3-core-datastore]]/[[04-p4-pipeline-datastore]] датасеты фигурируют под логическими именами
> `telemetry.parquet`, `lims.parquet`, `pak.parquet`. Это ссылки на датасет целиком
> (чтение через glob `scan_parquet("data/processed/242000__*.parquet")` и т. п.);
> физические имена — только по формуле выше.

Правила имён[^p3names]:

1. Все имена — `snake_case`, разрешены `[a-z0-9_.]`; разделитель уровней имени — `__`, внутри уровня — `_`. Код тега сохраняет исходный регистр производителя (`24-2000.P8`, `Mg.Sulfur`), но в `tag_code` как значении колонки — как в источнике, без переименований.
2. Имя тега = код КИП из CSV, не описание: «Тегам доверять по поведению значений, не по описанию».
3. Запрещены пробелы, кириллица и даты в имени вне `{yyyy}`.

## 2. Партиционирование

| Датасет | Ключ партиции | Гранулярность | Оценка файлов |
| --- | --- | --- | --- |
| телеметрия 24-2000 | `{tag}__{yyyy}` | год × тег | 26 тегов × 4 года ≈ 104 |
| телеметрия АВТ | `{tag}__{yyyy}` | год × тег | 70 тегов × 4 года ≈ 280 |
| ЛИМС | `{yyyy}` | год | 4 |
| ПАК | `{yyyy}` | год | 4 |

- Партиция — год записи `ts` (UTC); файл целиком лежит в одном году, строки не делятся.
- 10-минутная сетка телеметрии без пропусков даёт ≈ 52 560 точек/год на тег — комфортный размер файла для `scan_parquet` и точечной досборки нужного диапазона.
- ЛИМС и ПАК — разреженные (медиана 24 ч и 10 мин соответственно), годовая партиция достаточна; дробить дальше незачем.

## 3. Время и физические типы

Глобальная таблица форм (§0) — обязательна для всех датасетов:

| Аспект | Правило |
| --- | --- |
| Время | `timestamp[ms, UTC]` во всех колонках времени и в именах артефактов |
| Часовой пояс | единый во всех источниках: «**Часовой пояс единый** во всех источниках»; приводится к UTC при инжесте, внутри Parquet всегда UTC |
| Nullable-значения | `value: float64`, NaN = «нет значения»; JSON-представления NaN не допускают — только `null` |
| Енумы | `quality_flag`, `source`, `status` → `dictionary<string>` со значениями `lower_snake` |
| Категориальные коды | `tag_code`, `point_id`, `indicator`, `unit` → `dictionary<string>` (мало уникальных, много повторов) |
| Сжатие | Parquet + zstd для всех файлов `data/processed/` |

## 4. Только-добавление и версии каталогов

> [!warning] История не переписывается
> «Изменение схемы датасета — только новой версией каталога (v1→v2), история не переписывается».

1. Повторный запуск пайплайна перезаписывает только партиции, пересчитанные из изменившегося `raw/`; добавление новых дат в тот же год — дозапись/пересборка партиции, не новый формат.
2. Ломающее изменение схемы (новая колонка с изменением смысла, другой тип, другой состав `quality_flag`) → новый каталог данных `data/processed_v2/…`; старый не трогается до явной архивации.
3. Версия каталога фиксируется в `datasets_manifest.json` (`catalog_version`) и попадает в `versions` отчёта прогона.
4. Поля не добавляются молча: «каждый документ датасета — контракт „писатель (data-pipeline) ↔ читатель (core)“: поля не добавляются молча».

## 5. Хэши данных и воспроизводимость

Каждая запись обновляет манифест — каждая запись обновляет `datasets_manifest.json` (sha256, диапазон дат, версия пайплайна); `data_hashes` берётся из него (см. [[04-p4-pipeline-datastore]]) отчёта A.7»:

```json
{
  "catalog_version": "v1",
  "pipeline_version": "0.3.0",
  "datasets": {
    "242000__Q21__2024.parquet": {
      "sha256": "9f2c…e1",
      "row_count": 52560,
      "date_min": "2024-01-01T00:00:00Z",
      "date_max": "2024-12-31T23:50:00Z"
    }
  }
}
```

- `data_hashes` в `RunReport` ([[07-run-report]]) — агрегат sha256 всех партиций, прочитанных прогоном; так «один seed → одно решение» проверяется вместе с одинаковым входом (правило детерминизма).
- Хэш считается по содержимому файла, не по имени: пересборка партиции с теми же строками даёт тот же хэш (детерминированный порядок строк по `ts` обязателен).
- Свежесть/приоритет источников при чтении нескольких датасетов — домен data-pipeline ([[03-sync-freshness]]); data-store хранит только готовый снимок `freshness.parquet`.

## 6. Проверка целостности

> [!example] Чек-лист перед публикацией партиции (выполняет data-pipeline, проверяет core при первом чтении)
> 1. Имя файла совпадает с формулой §1 и содержимым (`tag`, `yyyy` — из данных).
> 2. `ts` — `timestamp[ms, UTC]`, строго монотонно не убывает в пределах файла.
> 3. Нет значений сентинелов {307, 251, 252, 240} в `value` — только в `data/raw/`.
> 4. Каждый NaN имеет `quality_flag` ≠ `ok`; каждый `ok` — непустой NaN-свободный `value`.
> 5. sha256 записан в `datasets_manifest.json`.

[^p3names]: Правила P3: «**рантайм read-only по `data/processed/`** — ядро туда не пишет; запись только в `artifacts/`; имена `snake_case`; время UTC».
